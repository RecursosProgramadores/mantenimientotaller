# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MantePro: an industrial maintenance-management SPA (Spanish UI) for a single institution ("taller" = workshop). It tracks machines, preventive/corrective maintenance orders (OTMs), external workshop repairs, spare-parts stock, technicians, usage-hour cycles/thresholds, and notifications. Frontend is TanStack Start/Router + React 19 + Tailwind v4 + shadcn/radix UI; backend is entirely Supabase (Postgres + Auth + Storage + Realtime). There is no custom API layer — components talk to Supabase directly.

Deployment target is **GitHub Pages as a static SPA** (see `.github/workflows/deploy.yml`: `vite build` → upload `dist`), not TanStack Start SSR. `src/server.ts` / `src/start.ts` are framework scaffolding not exercised by the actual deployment.

## Architecture

### Routing
File-based routing via TanStack Router, generated into `src/routeTree.gen.ts` (**never edit that file by hand** — it's regenerated by the `TanStackRouterVite` plugin from `vite.config.ts`). Route files live in `src/routes/`; see `src/routes/README.md` for the file-naming conventions (`$id` dynamic segments, `_layout` layouts, `__root.tsx` app shell). The router uses `createBrowserHistory()` with `basepath: "/mantenimientotaller/"` (see comment in `src/router.tsx` explaining why — GitHub Pages + clean URLs need `public/404.html` as an SPA-fallback trick for direct/refreshed deep links).

`src/routes/__root.tsx` nests the global providers in this order: `ThemeProvider` → `QueryClientProvider` → `AuthProvider` → `MantePoProvider` → `AppGate` (shows `LoadingScreen` while auth/session or first data fetch is in flight) → `Outlet`. Each actual page route wraps its content in `<AppShell>` (`src/components/AppShell.tsx`), which itself wraps children in `<ProtectedRoute>` — so auth gating happens per-page via `AppShell`, not centrally in `__root.tsx`.

### State management — `src/context/MantePro.tsx`
This is the app's central nervous system: one large context (`MantePoProvider` / `useMantePro()`) holding all domain entities in React state (machines, maintenance types, OTMs/records, workshops, workshop-records, spare parts, technicians, settings, usage logs/cycles, notifications) plus every CRUD action for them. There is no per-entity store/reducer split and no client-side cache layer (TanStack Query's `QueryClient` is provided in context but not actually used for data fetching here).

Pattern to follow when extending it:
- `fetchAllData()` does one big pull from Supabase (joined selects) and repopulates all state. Almost every mutation (`addX`/`updateX`/`deleteX`) ends by calling `fetchAllData()` again rather than doing optimistic local updates — keep this pattern for consistency rather than introducing partial local mutation.
- Deletes are logical, not physical, for entities with history referencing them (`activo = false` on `maquinas`, `tipos_mantenimiento`, `talleres_externos`, `usuarios`) — physical deletes are only used where there's no dependent history (e.g. `ordenes_trabajo`, `repuestos_catalogo`, notifications).
- The app is **single-tenant**: `resolveInstitucionId()` always resolves to "the" one row in `instituciones` (ordered by `created_at` to be deterministic even if duplicates exist) rather than taking a tenant id from auth/context.
- Field names are translated at the boundary: TS/UI types use English-ish camelCase (`Machine`, `MaintenanceRecord`, etc.) while every Supabase table/column is Spanish snake_case (`maquinas`, `ordenes_trabajo`, `numero_otm`, ...). Don't rename either side to "match" — the mapping is intentional and happens in the `fetchAllData` selects and in each mutation's payload-building.
- File uploads (machine photos, institution logo, machine/workshop documents) go to Supabase Storage buckets (`maquinas-fotos`, `documentos-otm`, `documentos-taller`); base64 `data:` URLs are the local/pending representation before upload, detected via `.startsWith('data:...')`.
- A realtime subscription (`supabase.channel('public_schema')`) refetches all data on `uso_ciclos` UPDATE, new `notificaciones`, and `ordenes_trabajo` reaching `estado: 'Completado'`.
- Several invariants are enforced server-side and must stay that way rather than being re-derived on the client: `numero_otm` is generated by a DB trigger (client never sends it), threshold-crossing notifications are created by the `tg_notificar_umbral` trigger, and `uso_ciclos.horas_acumuladas` is incremented by a trigger when a `uso_logs` row is inserted.
- Machine status `"En Taller"` is only allowed to be set via the "send to workshop" flow (`addWorkshopRecord`), which also flips `maquinas.estado`; setting it directly through `updateMachine` is blocked client-side unless a matching active `envios_taller` row already exists, to avoid machines getting stuck in that state with no real workshop record behind them.
- When `envios_taller` (workshop record) rows are closed/deleted/reopened, the linked machine's `estado` is kept in sync in the same function — don't add a workshop-record mutation without mirroring that sync.
- Spare-part stock (`repuestos_catalogo.stock_minimo`) is adjusted by `adjustCatalogStock()` whenever OTM parts are added/edited/removed — matched by case-insensitive exact name against the catalog; parts typed freehand that don't match any catalog entry simply don't affect stock.

### Auth — `src/context/AuthContext.tsx`
Wraps Supabase Auth (`supabase.auth`), and on sign-in loads an app-level profile from the `usuarios` table (joined by `auth_user_id`) for `name`/`role`/`avatar` — falling back to a synthesized profile if no row exists. Route-level gating is via `<ProtectedRoute>` (redirects to `/login` when not authenticated), used inside `AppShell` per page rather than globally.

### Database — `supabase/migrations/`
Plain numbered SQL migration files (no Supabase CLI project scaffolding beyond the `migrations/` folder) — read them sequentially to understand schema evolution; later files patch/fix earlier ones (e.g. `003_fix_institucion_singleton.sql`, `012_fix_accion_tipo_notificaciones.sql`) rather than the schema being redefined from scratch. Core tables: `instituciones`, `areas`, `usuarios`, `maquinas`, `tipos_mantenimiento`/`actividades_tipo`, `ordenes_trabajo`/`actividades_otm`/`repuestos_otm`, `componentes_criticos`, `uso_ciclos`/`uso_logs`, `talleres_externos`/`envios_taller`/`seguimiento_taller`/`componentes_afectados`, `documentos`, `notificaciones`, `repuestos_catalogo`. When adding a migration, follow the existing numbered-file convention and treat prior migrations as immutable history.

### UI layer
`src/components/ui/*` is shadcn/ui (`components.json`: style `new-york`, Tailwind CSS variables, `@` import alias to `src/`) — treat these as generated/vendored primitives, and extend by composition in `src/components/*.tsx` (e.g. `MachineFormDialog.tsx`, `MaintenanceFormDialog.tsx`) rather than editing the primitives. Styling is Tailwind v4 via the `@tailwindcss/vite` plugin, configured through `src/styles.css` (no separate `tailwind.config.*`).

### Code style
ESLint flat config (`eslint.config.js`) integrates Prettier as a lint rule (format issues surface as lint errors); `@typescript-eslint/no-unused-vars` is deliberately off. Prettier: 100-char width, double quotes, semicolons, trailing commas everywhere (`.prettierrc`). `noUnusedLocals`/`noUnusedParameters` are off in `tsconfig.json`. Comments throughout `MantePro.tsx` documenting *why* a fix was made (referencing prior bugs like "MAQ-002") are intentional history — preserve that style when fixing similar bugs rather than deleting the context.
